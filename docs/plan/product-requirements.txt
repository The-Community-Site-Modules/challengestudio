1. How to Use This Document

This document is the product source of truth for the initial planning and build of Challenge Studio. It
defines what the product is intended to become, which capabilities belong in the first release, how the
major workflows should operate, and which technical boundaries must remain intact.
 The developer should first use this document to produce a written technical plan, architecture

     proposal, phased work breakdown, risk list, and questions requiring owner decisions.
 This document is not authorization to implement every future feature in one build. The MVP and

     later-roadmap boundaries are deliberate.
 Any proposed change that narrows the product vision, changes ownership, introduces third-party

     lock-in, or makes Community Site integration harder must be raised before implementation.
 Database schema concepts in this document are design guidance. Production database changes must

     be separately reviewed and approved before being applied.

First deliverable expected from the developer
A Claude-assisted build plan that maps this specification into milestones, architecture, routes,
components, data entities, permissions, tests, deployment steps, and clearly identified owner decisions.

2. Executive Summary

Challenge Studio is a multi-tenant SaaS product that lets creators, coaches, authors, speakers, educators,
ministries, businesses, agencies, and community leaders create structured challenge experiences. Those
experiences may be short marketing events, paid programs, evergreen lead magnets, internal member-
engagement campaigns, team challenges, or longer transformation journeys.

The core product insight is that a challenge is not simply a list of daily tasks. It is a guided transformation
with a beginning state, a desired outcome, daily milestones, evidence of progress, community
reinforcement, and a meaningful finish. Challenge Studio should therefore feel more like a journey and
less like project-management software.

The standalone SaaS will provide its own creator accounts, workspaces, participants, public pages,
challenge administration, communications, and analytics. Its architecture must also preserve a clean
integration boundary so the same challenge engine can later operate as a paid add-on inside The
Community Site, using Community Site identity, membership, branding, entitlements, and community
capabilities where appropriate.

3. Product Vision and Strategic Purpose

3.1 Product vision

Challenge Studio helps leaders turn an idea, method, or desired outcome into an organized, motivating
experience that people actually complete. It should make it possible to launch a polished challenge
without assembling a patchwork of landing-page software, email tools, Facebook Groups, spreadsheets,
Zoom links, course systems, and manual follow-up.

3.2 Strategic opportunity

 Replace the common Facebook Group plus email sequence approach used for 5-day marketing

 Give existing communities a repeatable way to create engagement, accountability, and visible

3.3 Product promise

Product promise
Build a challenge. Guide a transformation. Turn participation into momentum, community, and

3.4 Non-goals for the first release

 Challenge Studio is not initially a full learning-management system or replacement for every course
     platform.

 It is not initially a general CRM, full email-marketing platform, webinar platform, or payment
     processor.

 It should integrate with or provide focused versions of those capabilities only where they directly
     serve a challenge workflow.

 It should not attempt marketplace distribution, advanced AI generation, native mobile apps, complex
     affiliate management, or agency white labeling in the first MVP.

6.1 Challenge timing models

 Fixed calendar: all participants see the same active day.
 Rolling enrollment: each participant has an individual Day 1.
 Open access: all published days are available.
 Sequential completion: the next step unlocks after required completion.
 Scheduled release: days unlock at configured dates/times.
 Weekly release: groups of content unlock by week.

6.2 Challenge duration

The product must not hard-code common lengths. A creator may build a 3-day, 5-day, 7-day, 21-day, 30-
day, 90-day, 365-day, or milestone-based experience. Presets may speed configuration, but the data model
should support arbitrary durations and optional rest or catch-up days.

8.1 Creator launches a 5-day marketing challenge

34. Create a workspace or enter an existing workspace.

36. Enter the promise, participant starting point, destination, title, summary, dates, timezone, and

     expected daily commitment.
37. Configure public registration, required form fields, consent language, welcome page, and challenge

44. Visits a branded registration page and submits required details.

48. Completes each day, submits evidence or reflection, interacts with participants, and attends live

     sessions.
49. Receives progress celebrations, reminders, and catch-up guidance.
50. Completes the final day, receives a badge or certificate, and sees the creator's next-step offer.

12.1 Lead data and consent

Registration should capture only configured fields and must preserve consent timestamps, source/UTM
fields, and acceptance of applicable terms. Export and integration capabilities should respect privacy
settings and workspace permissions.

12.2 Offer capability boundary

and revenue attribution can be introduced only after billing ownership, Stripe architecture, taxes,
refunds, and entitlement behavior are separately designed.

15.1 MVP communications boundary

The MVP should use reliable transactional email for challenge-related messages. It does not need to
become a complete broadcast email-marketing system. Creators should be able to enable/disable core
message types and edit a controlled set of subject/body fields with safe template variables.

15.2 Notification preferences

Participants must be able to manage nonessential challenge email preferences while still receiving
security, access, and legally required messages. Workspace unsubscribe behavior should not accidentally
unsubscribe a person from unrelated products or workspaces.

16. Live Sessions and Events

 Creators can schedule zero or more live sessions with title, date/time, timezone, description, host, join
     URL, and replay URL.

 Participants see sessions in the challenge hub and relevant daily pages.
 Calendar-file download should be supported in MVP if feasible.
 Zoom OAuth, native meeting creation, attendance sync, and automated replay ingestion are later

     integrations.
 External join URLs must be protected from public discovery when the challenge is private.

19.1 Suggested initial stack

The expected implementation direction is a modern Next.js application deployed to Vercel, with
TypeScript, a relational database, secure object storage, and a server-side authorization layer. The
developer should propose exact versions and supporting libraries based on maintainability, security, and
compatibility rather than novelty.

19.2 Billing readiness

The domain model should be ready for future workspace subscriptions and usage limits, but production
billing should not be activated until products, prices, entitlements, lifecycle states, cancellation, failed-
payment handling, and webhook idempotency are separately approved.

20. The Community Site Module
Integration

The Community Site treats paid modules as independent products. Challenge Studio must be designed so
it can be licensed and activated for eligible Community Site tenants without merging its internal domain
logic into unrelated native features.

20.1 Integration goals

 Use Community Site member identity through a secure trusted integration rather than requiring
     duplicate accounts.

 Resolve a Community Site tenant to a Challenge Studio workspace or integration installation.
 Inherit site branding by default while allowing challenge-level presentation settings.
 Restrict access based on Community Site site entitlements, module license status, membership, group,

     or offer access.
 Expose challenge navigation and participant experiences inside the community shell or through a

     seamless module route.
 Allow selected challenge events to appear in Community Site feeds and notifications without

     duplicating all social data.
 Provide installation, deactivation, grace-period, and data-export behavior.

20.3 Entitlement principle

Integration code must check explicit module and feature entitlements, not assume access based only on
plan names. The Community Site strategy allows eligible Community and Creator Core sites to purchase
modules, while module compatibility may vary by required native capabilities.

20.4 API and identity approach

The developer should propose a signed server-to-server installation and launch model. Browser-supplied
site IDs or role claims must never be trusted without server validation. The integration should support
token expiry, replay protection, tenant binding, user binding, and revocation.

requirements when registration is enabled, and test whether referenced files/resources exist.
